1. PROJECT
OVERVIEW ============================================================

CyberGuard AI is a web-based cybersecurity analysis platform. It brings
four different analysis tools into one website:

1.  Phishing Link Scanner
2.  Emoji & Text Hidden-Code Scanner
3.  Photo Hidden-Code Scanner
4.  DeepFake & AI-Image Forensics Scanner

The purpose is to inspect submitted links, text and image files for
suspicious indicators and explain what the scanner found. It is an
educational analysis and awareness tool. It is not a certified
antivirus, a complete malware sandbox, or a guaranteed deepfake
detector.

IMPORTANT TERMINOLOGY: The project uses rule-based checks, file/metadata
inspection, pattern matching, statistical heuristics and a small
logistic-formula risk model for link analysis. Do not claim that it uses
a trained neural network or that every scanner is a trained AI model.
The product name contains “AI”, but the implementation should be
described accurately.

============================================================ 
2. HOW THE WEBSITE WORKS: OVERALL ARCHITECTURE
============================================================

FRONTEND: - HTML provides the structure of the pages. - CSS controls
layout, colours, typography and visual appearance. - JavaScript handles
user interactions, sends requests and displays results.

BACKEND: - Python server.py receives HTTP requests. - It validates the
input and sends it to the relevant analysis function. - The analysis
function runs the scanner’s checks and prepares a result.

COMMUNICATION: - The browser sends HTTP POST requests to the backend
API. - JSON is used for text and URL input. - Image bytes are sent for
image uploads. - The backend returns a JSON response. - JavaScript reads
the response and displays the verdict, score, layers and report.

API ENDPOINTS: - POST /api/link -> phishing link analysis - POST
/api/emoji -> emoji/text Unicode analysis - POST /api/photo -> image
hidden-content analysis - POST /api/deepfake -> AI-image/deepfake
forensic analysis - GET /health -> server health check

HEALTH CHECK: The /health endpoint returns a small JSON response showing
that the web server is responding. It does not run a scan.

HOSTING: - The source code is maintained in GitHub. - The website is
deployed on Render. - In public mode, the Python server reads Render’s
PORT environment variable and binds to 0.0.0.0. - In local Windows mode,
run.bat starts the server on localhost and opens the browser. - Public
mode does not automatically open a browser.

============================================================ 3. HOW TO
UNDERSTAND THE LAYER RESULTS
============================================================

Each scanner divides its checks into eight layers. A layer reports: -
Name: what type of check was performed. - Risk: a numeric risk
contribution generated by the program’s rules. - Status: OK, WARN or
BAD. - Details: evidence or explanation found by that check.

A risk score is an indicator generated by the program’s own rules. It is
not a certified probability of an attack. Different scanners use
different score aggregation rules and different thresholds. Do not
compare scores from different scanners as if they were calibrated on the
same scale.

============================================================ 4. PHISHING
LINK SCANNER — ALL 8 LAYERS
============================================================

PURPOSE: To examine a URL for suspicious structure, possible brand
impersonation, risky wording, DNS information, TLS certificate
information, page behaviour, domain registration age and heuristic risk
indicators.

LAYER 1 — URL STRUCTURE What it checks: - Whether the URL uses HTTPS or
plain HTTP. - Whether the host is a raw IP address rather than a domain
name. - Whether the URL contains an @ symbol in its network location. -
Whether the URL is unusually long. - Whether it has many subdomain
levels. - Whether the hostname contains many hyphens. - Whether it uses
an unusual port. - Whether it contains Punycode (xn–), which can
represent international characters that resemble other letters. -
Whether percent-encoded characters appear in the URL.

Why it matters: Attackers may create long or complicated URLs, use
misleading subdomains, unusual ports, raw IP addresses or look-alike
internationalised domain names to make a destination harder to
recognise.

Important limitation: HTTPS means the connection is encrypted; it does
not prove that the website itself is trustworthy. Percent encoding and
long URLs can also be legitimate.

LAYER 2 — BRAND IMPERSONATION & REPUTATION What it checks: - Compares
the domain against a built-in list of recognised brands and their
official domains. - Normalises some look-alike characters, such as 0/o,
1/l, 3/e, 5/s, rn/m and vv/w. - Checks whether a brand name appears in a
domain that is not one of its listed official domains. - Uses
edit-distance comparison to detect some misspelled or look-alike domain
names. - Recognises domains on its trusted list.

Why it matters: A deceptive website may use a brand name or a slightly
altered spelling to look like a genuine service.

Important limitation: The trusted list is not a complete live reputation
database. A domain missing from the list is unknown, not automatically
malicious. A new or uncommon legitimate domain may be flagged, and
sophisticated impersonation may be missed.

LAYER 3 — LEXICAL, TLD & SHORTENER ANALYSIS What it checks: - Looks for
phishing-related words in the hostname, path and query string. - Checks
whether the top-level domain is in the program’s configured higher-risk
TLD list. - Detects known URL-shortener domains. - Looks for
redirect-style query parameters such as url, redirect, next, goto or
link when they contain an HTTP destination.

Why it matters: Words related to account verification, login or urgent
action can be used in deceptive links. Shorteners can hide the final
destination. Redirect parameters can make the final destination less
obvious.

Important limitation: A suspicious word or TLD is not proof of phishing.
Many legitimate websites use URL shorteners and redirect parameters.

LAYER 4 — DNS LOOKUP What it checks: - Resolves the hostname to IP
addresses. - Displays some resolved addresses. - Checks whether an
address is private or non-public. - Uses an operating-system DNS tool
where available, such as a PowerShell or Linux shell command, and
records the tool/output.

Why it matters: DNS translates a domain name into the IP address used to
reach a server. A domain that does not resolve may be mistyped, offline
or unavailable. A public website resolving to a private/non-public
address is an important warning sign.

Important limitation: DNS results can change, and a failed lookup can be
caused by network or DNS problems. DNS resolution alone cannot establish
whether a site is safe.

LAYER 5 — TLS / SSL CERTIFICATE What it checks in local mode: - Attempts
a TLS connection. - Checks certificate verification. - Reads certificate
issuer information. - Reads the certificate start date and estimates how
old the certificate is. - Reports the negotiated TLS version where
available.

Why it matters: TLS protects data while it travels between the
browser/client and server. A certificate verification failure can
indicate a configuration problem or an untrusted connection.

IMPORTANT PUBLIC-DEPLOYMENT BEHAVIOUR: The public Render version blocks
visitor-controlled outbound TLS inspection as an SSRF safety measure. If
the result says “NOT PERFORMED on this public server”, this check was
deliberately skipped. Do not tell the teacher that a TLS check was
completed in that scan.

Important limitation: A valid TLS certificate proves control of a domain
for encrypted communication; it does not prove that the site is honest.
New certificates are common and are not automatically malicious.

LAYER 6 — LIVE CONTENT & REDIRECT ANALYSIS What it checks in local
mode: - Attempts to fetch the page. - Checks the HTTP response status
and content type. - Inspects redirect destinations and the number of
redirects. - Checks whether the response appears to trigger a file
download. - Reads the page title. - Looks for password input fields. -
Looks for forms that submit information to a different domain. - Looks
for some obfuscated JavaScript markers. - Looks for hidden iframes,
meta-refresh redirects and right-click-blocking scripts.

Why it matters: The page itself may reveal behaviours that are not
visible from the URL alone, such as credential forms or redirects to
another domain.

IMPORTANT PUBLIC-DEPLOYMENT BEHAVIOUR: The public Render version blocks
visitor-controlled live page fetching as an SSRF safety measure. If the
result says “NOT PERFORMED on this public server”, live content
inspection was not performed. The scanner still performs the other
available URL checks.

Important limitation: Even when page fetching is available, simple
pattern checks cannot understand every script or prove that a page is
malicious. Legitimate websites may use redirects, forms, scripts and
downloads.

LAYER 7 — DOMAIN AGE (RDAP REGISTRY) What it checks: - Queries public
RDAP registration information for the domain. - Attempts to read the
registration event date. - Calculates approximately how many days ago
the domain was registered. - Gives higher risk contributions to very
recently registered domains.

Why it matters: Some phishing domains are created shortly before being
used. A very new domain can therefore be a useful warning indicator.

Important limitation: Many legitimate websites are new, and old domains
can also be compromised. Registration information may be unavailable or
hidden. Domain age alone is not a verdict.

LAYER 8 — MACHINE-LEARNING RISK MODEL (IMPLEMENTATION ACCURACY) What it
checks: The code calculates a logistic-formula score using URL
characteristics such as: - URL length - Number of subdomains - Number of
hyphens - Ratio of digits in the hostname - Character entropy - Number
of suspicious keywords - Whether HTTPS is used - Whether the host is a
raw IP address - Whether an @ symbol is present - Whether the TLD is in
the configured list

The formula converts a weighted combination of these features into a
value between 0 and 1, then displays it as a percentage-like model
score.

IMPORTANT: This is a hand-coded logistic heuristic/formula in the source
code. It is not a trained machine-learning model and it has no
demonstrated training dataset or measured accuracy. If the teacher asks,
explain this honestly: “It is a logistic-formula risk model based on
manually selected URL features, not a trained ML classifier.”

LINK SCAN OVERALL SCORE: The program combines the eight layer risk
values using a weighted average and the maximum layer risk. It gives the
strongest layer extra influence. A trusted listed domain can receive a
strong score reduction if the brand/reputation layer has low risk. The
final score is capped at 100.

Link result labels: - Below 25: Likely Safe - 25 to 49: Suspicious - be
careful - 50 and above: Phishing / Dangerous

These are the program’s own heuristic labels, not a guarantee.

============================================================ 5. EMOJI &
TEXT HIDDEN-CODE SCANNER — ALL 8 LAYERS
============================================================

PURPOSE: To inspect pasted text and emoji sequences for invisible
Unicode characters, hidden data, suspicious control characters,
excessive combining marks, code-like patterns and Base64-encoded
content.

LAYER 1 — ZERO-WIDTH STEGANOGRAPHY What it checks: - Looks for
zero-width space (U+200B) and zero-width non-joiner (U+200C). - Treats
these characters as possible binary symbols in the implemented decoding
method. - If enough characters are present, attempts to decode the bit
sequence into readable text.

Why it matters: Zero-width characters are not normally visible in
rendered text. They can sometimes be used to carry hidden information
inside text that looks ordinary.

Important limitation: Zero-width characters also have legitimate
typography and language uses. Their presence does not automatically mean
an attack. The scanner’s decoding method only detects the specific
pattern it implements.

LAYER 2 — UNICODE TAG CHARACTERS (HIDDEN ASCII) What it checks: -
Detects Unicode TAG characters. - Converts the relevant tag code points
back into their corresponding ASCII characters. - Displays recovered
text. - Treats the recognised England, Scotland and Wales flag tag
sequences as legitimate exceptions.

Why it matters: Tag characters are generally invisible in normal text
display. A sequence can therefore carry text that a reader may not
notice.

Important limitation: Some tag sequences are used legitimately,
especially in flag emoji. The scanner includes exceptions for several
recognised flag sequences, but it is not a universal Unicode policy
engine.

LAYER 3 — VARIATION-SELECTOR SMUGGLING What it checks: - Finds variation
selector code points. - Attempts to interpret selected
variation-selector values as bytes. - Tries UTF-8 decoding. - Requires a
minimum number of selectors and sufficiently readable output before
reporting recovered hidden text.

Why it matters: Variation selectors normally control how a character or
emoji is displayed. Unusual sequences may be examined for possible
hidden data.

Important limitation: Variation selectors are widely used for legitimate
text and emoji presentation. The scanner’s byte-decoding approach only
detects certain patterns; it cannot detect every possible steganographic
technique.

LAYER 4 — BIDIRECTIONAL (TROJAN-SOURCE) CONTROLS What it checks: - Looks
for Unicode bidirectional control characters. - These characters can
affect the displayed order of text. - Reports their presence and count.

Why it matters: Direction controls can make text appear in a different
visual order from its logical character order. This can be abused to
disguise file names, links or code.

Important limitation: Bidirectional controls are also needed for
legitimate right-to-left languages and mixed-direction text. Their
presence needs context.

LAYER 5 — CONTROL, PRIVATE-USE & UNASSIGNED CODE POINTS What it
checks: - Uses Unicode character categories to identify control
characters, private-use characters and unassigned code points. - Reports
the code points in U+ notation.

Why it matters: Some unusual or invisible characters can be used to
confuse text processing or hide information.

Important limitation: These categories have legitimate uses. A
private-use character may be part of a custom font or application. The
finding is an indicator, not proof of malicious intent.

LAYER 6 — CRASH, ZALGO & FLOOD PATTERNS What it checks: - Measures
consecutive combining marks. - Flags very long combining-mark runs. -
Checks for very large pasted text. - Checks for a single character
repeated thousands of times.

Why it matters: Extremely long combining sequences or huge repeated
inputs can make some applications slow, difficult to use or unstable.
Very large input can resemble a flooding pattern.

Important limitation: The scanner identifies suspicious patterns; it
does not actually attack or crash another application. Long text can be
legitimate.

LAYER 7 — CODE & COMMAND PATTERNS What it checks: Uses pattern matching
for examples of: - Script tags - JavaScript URI markers - Code execution
function names - PowerShell and Windows command patterns - Unix shell
command patterns - SQL injection-like strings - HTML event handlers -
Base64 data URI markers - Template-injection-like patterns - Path
traversal patterns - PHP code markers - URLs

Why it matters: These patterns may appear in scripts, commands or
injection attempts embedded in text.

Important limitation: Pattern matching is not code execution and does
not prove that a string is exploitable. Educational examples,
documentation and harmless code can also match. The scanner does not
execute the submitted text.

LAYER 8 — ENCODED PAYLOADS (BASE64) What it checks: - Searches the
visible/processed text and recovered hidden text for Base64-like data. -
Attempts to decode detected Base64 strings. - Displays decoded text
snippets when found.

Why it matters: Base64 is an encoding format often used to represent
binary or text data. It can be used to conceal readable content from
casual inspection.

Important limitation: Base64 is not encryption and is not automatically
malicious. It is commonly used for legitimate data transfer and storage.
Only detected candidate strings are decoded.

TEXT SCAN SCORE: The program adds the layer risk contributions and caps
the total at 100. - Below 20: Clean - nothing hidden found - 20 to 49:
Suspicious content - 50 and above: Dangerous - hidden payload detected

The result also includes a character-by-character table showing code
point, glyph, Unicode name, Unicode category, count, first position and
the scanner’s interpretation.

============================================================ 6. PHOTO
HIDDEN-CODE SCANNER — ALL 8 LAYERS
============================================================

PURPOSE: To inspect an uploaded image file’s actual binary structure,
metadata, embedded signatures, readable strings, encoded text, pixel
least-significant bits and structural anomalies.

IMPORTANT: This scanner analyses file data and hidden/embedded text. It
does not perform OCR on the visible words inside the picture.

LAYER 1 — FILE IDENTITY & EXTENSION CHECK What it checks: - Identifies
the image format using the file’s actual signature/content, rather than
trusting only the filename. - Compares the detected format with the file
extension. - Flags an unrecognised format or a mismatch between the
extension and actual content.

Why it matters: A file may be renamed with an image extension even
though its actual contents are not a recognised image format.

Important limitation: A mismatch may be accidental or caused by
conversion. It is a warning for investigation, not proof of malware.

LAYER 2 — STRUCTURE & TRAILING-DATA ANALYSIS What it checks: - Examines
whether extra bytes exist after the recognised end of the image. - If
more than the small tolerance used by the program is present, it
inspects the appended data. - Looks for known embedded file signatures
in that trailing data. - Displays a preview of the appended bytes where
appropriate.

Why it matters: A file can contain data after its normal image-ending
marker. That extra data may be harmless metadata or may indicate an
appended file/payload.

Important limitation: Some file formats and workflows can legitimately
contain extra data. Not every trailing byte is malicious.

LAYER 3 — METADATA TEXT (EXIF / XMP / PNG TEXT / COMMENTS) What it
checks: - Reads supported text metadata fields. - Examines EXIF-related
data and readable text. - Checks supported XMP, PNG text and comment
fields. - Runs suspicious-pattern checks against extracted metadata
text. - Displays metadata findings.

Why it matters: Metadata can contain information that is not visible in
the picture itself. It may include software details, comments or
suspicious strings.

Important limitation: Metadata can be removed, edited or absent in
normal images. Missing metadata does not prove that an image is
malicious or AI-generated.

LAYER 4 — EMBEDDED FILE SIGNATURES What it checks: - Searches file bytes
for known signatures associated with other file types, such as archives,
executables or scripts. - Reports matching signatures and byte offsets.

Why it matters: An image file may have another type of data embedded
inside it. Finding a known signature can be a reason to investigate the
file further.

Important limitation: A signature match is not a full file extraction or
malware scan. Some byte sequences can occur coincidentally.

LAYER 5 — SCRIPT & COMMAND PATTERNS IN FILE DATA What it checks: -
Extracts readable strings from the file. - Searches those strings for
script, shell, SQL, HTML, PHP, URL and other configured suspicious
patterns. - Displays matched pattern names and snippets.

Why it matters: Some embedded content may contain readable commands or
code-like strings.

Important limitation: A text match does not mean the image will execute
code. The scanner does not run the extracted commands or scripts.

LAYER 6 — ENCODED PAYLOADS (BASE64) What it checks: - Searches readable
strings and extracted metadata for Base64-like sequences. - Attempts to
decode candidate strings. - Displays decoded snippets and records them
as recovered content.

Why it matters: Encoded content may conceal text or data from a casual
viewer.

Important limitation: Base64 is a normal encoding format and is not
inherently malicious. Candidate detection can produce false positives
and may miss other encodings.

LAYER 7 — LSB PIXEL STEGANOGRAPHY What it checks: - For supported
lossless formats, obtains pixel data when available. - Reads the
least-significant bit (LSB) of pixel channel values. - Groups bits into
bytes. - Checks whether the beginning of the extracted bytes resembles
readable text. - Reports a possible hidden message when the implemented
readability conditions are met.

Why it matters: Changing the least-significant bit of a pixel value can
make a very small visual difference while storing information in the
image.

Important limitation: This implementation is a basic text-oriented LSB
check. It does not detect every steganography method. It is limited to
supported formats and available pixel extraction. JPEG is lossy and this
LSB check is not applied to JPEG in this code.

LAYER 8 — STRUCTURAL ANOMALIES & POLYGLOT INDICATORS What it checks: -
Looks for unusual PNG chunks outside the standard list. - Checks whether
appended data has unusually high entropy, which can be consistent with
compressed or encrypted data. - Reports parser errors or malformed-file
indicators. - Combines these findings into the layer result.

Why it matters: Unusual structure, appended data or malformed sections
may indicate a crafted file or a file containing multiple kinds of data.

Important limitation: High entropy can also be normal for compressed
content. An unusual chunk or parser warning does not automatically mean
an attack.

PHOTO SCAN SCORE: The program adds layer risk contributions and caps the
total at 100. - Below 20: Clean - no hidden code found - 20 to 49:
Suspicious file - 50 and above: Dangerous - hidden code detected

The report may include file facts, metadata text, readable strings and
recovered suspicious content.

============================================================ 7. DEEPFAKE
& AI-IMAGE FORENSICS SCANNER — ALL 8 LAYERS
============================================================

PURPOSE: To inspect an image for known AI-generator metadata markers,
provenance information, camera metadata, dimensions, editing traces and
selected pixel statistics.

VERY IMPORTANT: This is a heuristic forensic indicator tool. It is not a
trained deepfake-detection neural network and cannot prove whether a
person or image is real. Metadata can be stripped, edited or forged. A
genuine image can be edited, and an AI-generated image can have metadata
added.

LAYER 1 — CONTAINER & FORMAT PROFILE What it checks: - Identifies the
image format and file size. - Gives a small risk contribution to PNG and
WEBP in this implementation because they are common output formats of
some AI image tools.

Why it matters: The format provides basic context about the file.

Important limitation: PNG and WEBP are widely used for ordinary real
photographs and graphics. Format alone is a very weak signal and cannot
establish AI origin.

LAYER 2 — AI-GENERATOR SIGNATURES IN METADATA What it checks: - Searches
selected file bytes and metadata for known AI generator markers. - Looks
for terms associated with prompts, sampler settings, seeds, tool names
and workflow/parameters metadata. - Reports a recognised marker if
found.

Why it matters: Some image-generation tools store information about the
generation process in image metadata. A known marker can be stronger
evidence that a file passed through a particular generator.

Important limitation: Many platforms remove metadata when images are
downloaded or shared. Markers can also be modified or copied. No marker
does not prove that an image is real.

LAYER 3 — CONTENT CREDENTIALS (C2PA PROVENANCE) What it checks: - Looks
for indicators associated with C2PA / Content Credentials manifests in
the file data. - Reports whether a possible provenance manifest marker
is present.

Why it matters: Content Credentials can carry information about an
image’s origin and editing history.

Important limitation: This scanner only checks for marker presence. It
does not fully validate the cryptographic signature, certificate chain
or trust status of a C2PA manifest. Presence should be verified with a
dedicated C2PA validation tool. Absence is common and is not proof of AI
generation.

LAYER 4 — CAMERA / EXIF AUTHENTICITY What it checks: - Examines EXIF
metadata. - Looks for camera make/model-related strings from a
configured list. - Reports whether camera-related EXIF evidence was
found or is missing.

Why it matters: A camera image may contain make, model, lens or exposure
metadata. Its presence can provide supporting context about the image’s
capture history.

Important limitation: Social media, messaging apps and editing software
often strip EXIF data. AI images can also have metadata added. Missing
EXIF is not proof that an image is AI-generated.

LAYER 5 — DIMENSION FINGERPRINT What it checks: - Reads image width and
height. - Checks whether both dimensions are multiples of 64. - Checks
selected square dimensions such as 512, 768, 1024, 1536 or 2048.

Why it matters: Some image-generation workflows use dimensions aligned
to particular grids or common generation sizes.

Important limitation: Photographs and ordinary graphics can have exactly
the same dimensions. This is only a weak statistical clue.

LAYER 6 — EDITING SOFTWARE & METADATA STRIPPING What it checks: - Looks
for selected face-editing or face-swap tool names in the inspected file
bytes. - Looks for common editing software names such as Photoshop,
GIMP, Lightroom, Snapseed and Adobe. - Checks whether both text metadata
and EXIF metadata are absent.

Why it matters: Tool traces can provide clues that an image was edited
or processed. Completely missing metadata may indicate that metadata was
stripped during processing or sharing.

Important limitation: Editing software use does not mean deepfake
creation. Metadata stripping is common and can happen to genuine images.
A tool name in the file is not conclusive proof of manipulation.

LAYER 7 — PIXEL NOISE RESIDUAL (SENSOR GRAIN) What it checks: - Extracts
pixel data when supported. - Compares neighbouring pixel values. -
Calculates an average neighbour-pixel difference as a simple noise
indicator. - Uses the result as a heuristic clue about image texture.

Why it matters: Real camera images often contain sensor noise and
processing artefacts. Some generated images may have different texture
statistics.

Important limitation: Denoising, compression, resizing, low light and
camera processing can change noise. AI tools can add noise, and real
images can be very smooth. This is not a reliable standalone deepfake
detector.

LAYER 8 — COLOUR & GRADIENT STATISTICS What it checks: - Measures the
proportion of neighbouring pixel values that are very similar. -
Estimates colour variety from sampled pixel colours. - Uses
smooth-gradient and colour-variety combinations as a heuristic signal.

Why it matters: Some generated images may contain unusually smooth
gradients or texture statistics.

Important limitation: Illustrations, cartoons, studio photos, blurred
images and compressed images can also be smooth. These statistics cannot
identify a deepfake by themselves.

DEEPFAKE SCAN SCORE: The program adds the eight layer risk
contributions, applies a minimum score when a known generator marker is
found, subtracts a contribution when camera metadata is found, and
clamps the result between 0 and 100.

Result labels: - Below 35: No strong AI / deepfake evidence - 35 to 69:
Possibly AI-generated or edited - 70 and above: Likely AI-generated /
manipulated

These labels are heuristic interpretations, not verified probabilities.
The report itself explains that absence of evidence is not proof that an
image is real.

============================================================ 8. REPORT
GENERATION AND RESULT DISPLAY
============================================================

After a scan, the backend prepares a result containing: - Scanner
title - Submitted target or filename - Eight layer results - Risk
score - Verdict and level - Summary - Optional tables - Optional
recovered-content blocks - A text report

The text report includes the scan type, target, scan time, verdict,
score, summary and each layer’s status, risk and details. Additional
tables and recovered-content sections may also be included.

The frontend JavaScript reads the JSON response and displays the layer
cards, progress/risk indicators, tables and report content.

============================================================ 9. PUBLIC
DEPLOYMENT AND BASIC SECURITY
============================================================

The public server has several safeguards: - It reads the PORT
environment variable supplied by the hosting platform. - It binds to
0.0.0.0 in public mode so the hosting proxy can reach it. - It does not
open a browser in public mode. - It limits request and upload sizes. -
It validates JSON input. - It sanitises uploaded filenames. - It limits
the number of concurrent scans with a semaphore. - It returns safer
error messages to public visitors. - It adds security-related response
headers. - It provides a /health endpoint. - Public link scanning blocks
visitor-controlled outbound TLS and live-page fetch operations to reduce
SSRF risk.

SSRF means Server-Side Request Forgery. It is a vulnerability where an
attacker tricks a server into making requests to destinations the
attacker should not be able to access, such as internal network
services. Blocking arbitrary visitor-controlled outbound requests is an
important protection for a public scanning service.

If the public link scanner reports that TLS or live content inspection
was not performed, that is intentional in the public deployment. The
other available URL analysis layers still run.

============================================================ 10.
IMPORTANT DIFFERENCES BETWEEN THE FOUR SCANNERS
============================================================

LINK SCANNER: Analyses a URL and some domain/network/page
characteristics. It includes DNS and RDAP lookups. In public mode, live
TLS and page-fetch checks are deliberately blocked.

EMOJI/TEXT SCANNER: Analyses pasted Unicode text and character patterns.
It does not execute the submitted text.

PHOTO SCANNER: Analyses file structure, metadata, embedded signatures,
readable strings and a basic LSB text pattern. It does not OCR the
visible picture.

DEEPFAKE SCANNER: Analyses image metadata, format, dimensions, editing
traces and pixel statistics. It does not use a trained deepfake neural
network and cannot prove authenticity.

============================================================ 11.
QUESTIONS A COMPUTER SCIENCE TEACHER MAY ASK
============================================================

Q1. What is phishing? Phishing is a social-engineering attack where an
attacker tries to trick a person into revealing information or taking an
unsafe action, often through a deceptive message or website.

Q2. What is DNS? DNS stands for Domain Name System. It translates domain
names into IP addresses so systems can locate servers.

Q3. What is HTTPS? HTTPS is HTTP protected by TLS encryption. It helps
protect data while it travels between the client and server. It does not
prove that a website is trustworthy.

Q4. What is TLS/SSL? TLS is the modern protocol used to encrypt network
connections and authenticate a server using certificates. SSL is its
older predecessor.

Q5. What is Unicode? Unicode is a standard that assigns code points to
characters and symbols from writing systems around the world.

Q6. What is a zero-width character? It is a character that normally
occupies no visible width when rendered. Some zero-width characters have
legitimate text-layout uses.

Q7. What is steganography? Steganography is the practice of hiding
information inside another medium, such as text, image, audio or video.

Q8. What is metadata? Metadata is information about a file, such as
camera model, date, dimensions, software or other properties.

Q9. What is EXIF? EXIF is a metadata format commonly used in image files
to store camera and image-capture information.

Q10. What is Base64? Base64 is an encoding scheme that represents binary
data using a set of printable characters. It is encoding, not
encryption.

Q11. What is an API? An API is an interface through which software
components communicate. In this project, JavaScript sends requests to
Python API endpoints.

Q12. What is JSON? JSON is a text-based data format used to exchange
structured information. The backend returns scan results as JSON.

Q13. What is a heuristic? A heuristic is a practical rule or
approximation used to make an assessment when a definitive answer is
difficult. It can be useful but can make mistakes.

Q14. Is the link risk model trained machine learning? No. The current
implementation uses a manually coded logistic-formula risk model based
on selected URL features. It is not a trained ML model.

Q15. Is the deepfake scanner 100% accurate? No. It uses metadata and
image-statistics heuristics. It cannot prove whether an image is genuine
or AI-generated.

Q16. Why use Python? Python provides readable syntax and built-in
modules for HTTP serving, parsing, networking, file handling, Unicode
processing and image-byte analysis.

Q17. What is frontend? The frontend is the part of the application that
users see and interact with in the browser.

Q18. What is backend? The backend handles server-side logic, input
processing, scanning and API responses.

Q19. What is Render? Render is a cloud hosting platform used to make the
Python web application accessible through a public website URL.

Q20. What is GitHub? GitHub hosts and manages source code repositories
and supports version control workflows based on Git.

============================================================ 13. WHAT TO
SAY HONESTLY ABOUT PROJECT LIMITATIONS
============================================================

-   The system can produce false positives and false negatives.
-   It does not guarantee detection of every phishing link or hidden
    payload.
-   The trusted-brand and suspicious-TLD lists are configured lists, not
    a complete global threat-intelligence service.
-   The text and image pattern checks only recognise patterns
    implemented in the code.
-   The photo scanner does not perform OCR on visible image text.
-   The LSB check is basic and limited to supported lossless image
    formats.
-   The deepfake scanner is heuristic and does not prove image
    authenticity.
-   The link scanner’s TLS and live-page inspection are disabled in
    public mode for SSRF safety.
-   The logistic-formula link score is not a trained machine-learning
    classifier.

A good engineering explanation includes both what a system can do and
what it cannot reliably do.
